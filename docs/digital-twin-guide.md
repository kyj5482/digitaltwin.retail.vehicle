# 미국 판매법인 디지털 트윈 — 개발 가이드

> 판매법인 → 생산법인 → 운송 → 딜러 → 고객으로 이어지는 **업무 프로세스 전체를 디지털 트윈으로 구성**하고,
> 그 위에서 시뮬레이션을 돌려 판매량·영업이익·고객만족도 KPI의 트레이드오프를 사전에 검증하는 시스템의 개발 가이드.

---

## 1. 프로젝트 목표와 설계 철학

### 1.1 최우선 과제
- **판매 증대를 통한 이익 극대화**와 **고객 만족도 향상**을 동시에 달성.
- 세 KPI(판매량, 영업이익, 고객만족도)는 상충 관계가 존재한다:
  - 인센티브 ↑ → 판매량 ↑, 영업이익 ↓
  - 품질 강화 활동 ↑ → 고객만족도 ↑, 영업이익 ↓
  - 캠페인(리콜) 발생 → 품질비용 ↑, 딜러 서비스 포화 → 정비 예약 지연 → 고객만족도 ↓
- 따라서 **단일 지표 최적화가 아니라, 연결 고리 전체를 시뮬레이션해서 Action Item을 사전 도출**하는 것이 목적이다.

### 1.2 "업무의 디지털 트윈"이란
- 특정 공간·하드웨어의 3D 재현이 아니다. **회사 업무(프로세스·물류·재무·품질)의 상태와 흐름을 데이터로 재현**하는 것이다.
- 실제 차량의 이동을 화면에서 애니메이션으로 재현할 필요는 없다. 대신:
  - 모든 차량이 **VIN 단위로 생산→운송→Wholesale→Retail→A/S까지 이벤트 체인으로 연결**되어 있고,
  - 화면은 이를 **집계(aggregation)로 보여주되, 언제든 VIN 단위까지 드릴다운** 가능해야 한다.
- 트윈의 가치는 표현 방식에 크게 좌우된다. → §7의 3가지 프로토타입으로 표현 방식을 먼저 검증한다.

### 1.3 트윈의 3층 구조

| 층 | 역할 | 내용 |
|---|---|---|
| **State Layer** | 현재/과거의 사실 | VIN 이벤트 체인, 월별 집계 스냅샷 (Parquet) |
| **Model Layer** | 업무 로직의 수식화 | 주문→생산 리드타임, 운송 소요, 수요 탄력성, 품질비용 함수 등 교체 가능한 모델 |
| **Simulation Layer** | 미래 생성 | 과거 윈도우 + 시나리오 파라미터로 미래 데이터를 생성하고 BP와 비교 |

핵심 원칙: **State는 불변의 사실, Model은 교체 가능한 가설.** 상위단에서 알고리즘(모델)을 바꾸면
동일한 State 위에서 다른 미래가 생성되어야 한다. 이것이 "전략에 문제가 없는지 판단하는 수단"이 된다.

## 2. 도메인 모델

### 2.1 VIN 라이프사이클 (이벤트 체인의 축)

```
ORDERED ─▶ IN_PRODUCTION ─▶ PLANT_STOCK ─▶ IN_TRANSIT ─▶ (PORT_YARD) ─▶ DEALER_ARRIVAL
                                                                            = WHOLESALE 이벤트
        ─▶ DEALER_STOCK ─▶ RETAIL_SALE ─▶ IN_SERVICE(커넥티드 개통) ─▶ SERVICE_EVENT*
```

- 스테이지 전이 시마다 `vin_event` 레코드가 기록된다(현업 데이터에 이미 Status 기록 존재 → VIN별 운송 시간 계산 가능).
- **Wholesale = 딜러가 차량을 인수하는 시점**의 이벤트. VIN별 판매 이익이 기록되고 월별 집계된다.
- **Retail Sale** 시 커넥티드카가 개통되어 이후 차량 데이터·진단 데이터·VoC·수리 데이터가 같은 VIN에 연결된다.
- 생산 순서 ≠ 운송 순서: 운송 모드(선박/철도/트럭)는 적정 대수가 모여야 배정되므로, 배치(batch) 단위 전이를 모델링해야 한다.

### 2.2 핵심 엔티티

| 엔티티 | 주요 속성 | 비고 |
|---|---|---|
| `vehicle (VIN)` | model, model_year, trim, features[], color, plant, channel | 모든 이벤트의 조인 키 |
| `vin_event` | vin, stage, ts, location, meta | 스테이지 전이 로그 (append-only) |
| `plant` | id, country, transport_modes[], lead_time, capacity, constraints | 로컬 1 + 해외 2 |
| `order` | month, plant, model, trim, qty, dealer/channel 배정 | **현재 미보유 → Wholesale 역변환으로 생성** (§5) |
| `dealer` | id, region, state, lat/lng, service_capacity | 미 전역 위치 기반 |
| `wholesale` | vin, ts, dealer, channel(Retail/Fleet/Gov/Rental), unit_profit | 채널 구분 집계 필수 |
| `retail_sale` | vin, ts, dealer, customer_zip, incentive_amt | |
| `bp_plan` | year, model, trim_mix%, monthly_target, expected_profit | 연간 비즈니스 계획 |
| `marketing` | month, medium(TV/Social/Search), spend, impressions, clicks | 검색은 퍼포먼스 지표 보유 |
| `service_event` | vin, ts, dealer, type(Warranty/Campaign/CustomerPay), parts[], labor | Part 금액의 이익 기반 재산정 이슈 |
| `voc_case` | ts, vin?, category, source(VoC/Social) | 소셜과 카테고리 분류 체계 일원화 |
| `telematics/diagnostics` | vin, ts, dtc_codes, metrics | 품질/안전 분석, 사전 정비 예측의 입력 |

### 2.3 프로세스 → 트윈 매핑

| 업무 프로세스 | 트윈에서의 표현 | 시뮬레이션 파라미터 |
|---|---|---|
| ① 연간 BP (트림 Mix, 목표) | `bp_plan` 기준선 — 모든 화면에서 "BP 대비" 델타 | 트림 Mix %, 연간 목표, Feature 구성 |
| ② 마케팅 | 매체별 spend → 인지 → 딜러 방문 → 구매 퍼널 | 매체별 예산, 전환율 |
| ③ 월 주문/배정 | 월별 order → 공장 생산 → 운송 배정 | 공장별 배분, 생산 차질률, 운송 배치 크기 |
| ④ Wholesale | 딜러 인수 이벤트 + 채널별 이익 집계 | 채널 Mix, 대당 이익 |
| ⑤ Retail + A/S | 판매 + 서비스 이벤트 + VoC | 인센티브, 캠페인 발생, 서비스 케파 |

## 3. 데이터 아키텍처

### 3.1 스택

```
Parquet (레이크: 사실 데이터 + 생성된 미래 데이터)
   └─ DuckDB (백엔드 내 임베디드 쿼리 엔진)
        └─ Backend API (FastAPI 권장; /api/v1/*)
             └─ Frontend (디지털 트윈 UI: 월별 Play + 드릴다운)
```

- Parquet 파티셔닝: `dataset/scenario=<id>/month=YYYY-MM/*.parquet`
  - `scenario=actual` 이 실적, `scenario=<sim-id>` 가 생성된 미래. **동일 스키마**로 두어 프론트가 실적/시뮬을 같은 쿼리로 읽게 한다.
- 집계 우선: API는 기본적으로 사전 집계(모델×트림×지역×월)를 반환하고, 드릴다운 요청 시에만 VIN 레벨을 스캔.

### 3.2 API 설계 (초안)

```
GET  /api/v1/timeline/months                      # 재생 가능한 월 목록 (actual/simulated 구분)
GET  /api/v1/kpi?month=&scenario=                 # KPI 스냅샷 (retail, wholesale, profit, csi, days_supply)
GET  /api/v1/pipeline?month=&scenario=&model=     # 스테이지별 재고/유량 (파이프라인 뷰)
GET  /api/v1/geo?month=&metric=&scenario=         # 지역(state)별 메트릭 (지도 뷰)
GET  /api/v1/stock?month=&dim=model,color,region  # 딜러 재고 다차원 집계 (색상 레벨까지)
GET  /api/v1/vins?stage=&month=&filters…&limit=   # 드릴다운: 조건에 맞는 VIN 목록
GET  /api/v1/vin/{vin}/chain                      # VIN 이벤트 체인 전체 (생산→A/S)
POST /api/v1/scenario                             # 시나리오 생성 (파라미터 → 미래 데이터 생성 job)
GET  /api/v1/scenario/{id}/diff?vs=bp|actual      # BP/실적 대비 차이 시계열
GET  /api/v1/service/load?month=&region=          # 딜러 서비스 부하/예약 지연 (캠페인 영향)
```

- 모든 조회 API는 `scenario` 파라미터를 받는다 → **화면은 실적 재생과 시뮬레이션 재생을 같은 코드로 처리.**
- 응답은 집계 행 + `drill_hint`(어떤 API로 더 내려갈 수 있는지)를 포함해 UI의 드릴다운 체인을 표준화.

### 3.3 시간 축 처리
- 월(month)이 1차 재생 단위. 각 월은 **as-of 스냅샷**(그 달 말 기준 스테이지별 재고)과 **월간 유량**(그 달의 전이 건수)을 모두 가진다.
- 스냅샷은 `vin_event`에서 파생 가능하지만, 재생 성능을 위해 월별 사전 집계 Parquet을 물리화한다.
- VIN 드릴다운은 이벤트 원본을 조회 — 스냅샷과 원본의 정합성 검증 쿼리를 배치로 상시 수행.

## 4. 시뮬레이션 프레임워크

### 4.1 미래 데이터 생성 원리
1. **윈도우 선택**: 과거 데이터에서 기준 윈도우를 정한다 (예: 최근 3개월 Wholesale이 "적정"이라고 판단되면 그 3개월).
2. **베이스라인 생성**: 윈도우의 분포(모델×트림×지역×채널 Mix, 리드타임, 차질률, 품질 발생률)를 유지한 채 미래 월로 전개.
3. **시나리오 파라미터 적용**: 탄력성 모델로 베이스라인을 변형.
4. **하류 전파**: 판매 변화 → 주문 변화 → 생산 부하 → 운송 배치 → 딜러 재고 → 서비스 부하 → 만족도 순으로 **체인을 따라 전파**.
5. **BP 대비 비교**: 생성된 시계열을 `bp_plan`과 겹쳐 월별 차이를 산출.

### 4.2 시나리오 파라미터 (1차 목록)

| 파라미터 | 영향 체인 |
|---|---|
| 인센티브 ($/대) | Retail ↑ → 대당 마진 ↓ → 딜러 재고 소진 ↑ → 주문 필요량 ↑ |
| 마케팅 예산 (매체별) | 인지 ↑ → 딜러 방문 ↑ → Retail ↑ (매체별 전환율 상이) |
| 공장별 생산 배분 | 리드타임·운송비 변화, 공장 케파/차질 리스크 노출 변화 |
| 생산 차질 이벤트 (휴가/설비) | 해당 월 생산 ↓ → 딜러 재고 ↓ → 기회손실 |
| 품질 캠페인 발생 (모델 지정) | 품질비용 ↑, 서비스 예약 지연 ↑ → CSI ↓, Part 비용 이익 압박 |
| 트림 Mix 변경 | 대당 이익 변화, 특정 트림 생산 제약 노출 |
| Days Supply 목표 | 주문량 자동 산출의 기준 |

### 4.3 모델 플러그인 구조
- 각 업무 로직은 **동일 인터페이스의 교체 가능한 모델**로 구현한다:
  `model(state_t, params) → state_t+1`
- 예: `DemandModel`(수요), `ProductionModel`(생산/차질), `LogisticsModel`(운송 배치),
  `AllocationModel`(딜러 배정), `QualityCostModel`(품질비), `CsiModel`(만족도).
- v1은 규칙 기반(이동평균+탄력성), v2 이후 통계/ML 모델로 교체 — **인터페이스가 같으므로 UI는 무변경.**
- 업그레이드된 모델의 검증: 과거 구간을 잘라 hold-out 백테스트 (예: 2025년 데이터로 2026년 상반기 재현 → 실적과 오차 측정).

### 4.4 운송 배치 모델 (생산 순서 ≠ 운송 순서)
- 공장×운송모드×목적지 권역별로 **배치 임계치**(예: 선박 800대, 철도 편성 120대, 트럭 8대)를 두고,
  공장 재고가 임계치에 도달하면 배치가 출발하는 큐 모델로 구현.
- VIN별 실제 운송 시간 데이터로 모드별 소요 분포를 추정해 시뮬레이션 파라미터로 사용.

## 5. Wholesale → 주문 역변환 (주문 데이터 부재 대응)

현재 주문서 데이터가 없으므로 초기에는 다음으로 근사한다:

1. VIN별 `PLANT_STOCK → DEALER_ARRIVAL(Wholesale)` 이벤트에서 공장·모드별 리드타임 분포를 추정.
2. Wholesale 시점에서 리드타임을 역산해 **추정 생산 완료 시점**을, 생산 소요를 다시 역산해 **추정 주문 월**을 부여한다.
3. 역변환 레코드에는 `estimated=true` 플래그를 달아, 추후 실제 주문 데이터 수집 시 같은 스키마로 치환한다.
4. 검증: 역변환된 월별 주문량이 공장 케파·실제 생산 이벤트와 모순되지 않는지 체크.

## 6. KPI 정의와 트레이드오프 모델

| KPI | 산식 (초안) |
|---|---|
| 판매량 | 월별 Retail Sales (채널 구분: Retail / Fleet / Gov / Rental 별도 집계) |
| 영업이익 | Σ(대당 기준 마진) − 인센티브 − 품질비용(워런티+캠페인 Part/공임) − 운송비 − 마케팅비 |
| 고객만족도 | 지수(0–100): 기준치 − f(서비스 예약 지연, VoC 발생률, 캠페인 노출) + f(사전정비 적중) |
| Days Supply | 딜러 재고 ÷ 최근 판매 속도 (지역·모델·트림·색상 차원까지) |

- **Part 금액 이슈**: 워런티/캠페인 수리의 Part 단가는 이익 기반으로 재산정되어야 함 →
  `QualityCostModel`에 Part 단가 정책(딜러 유리 / 이익 기반)을 파라미터로 두고 이익 영향을 시뮬레이션.
- **사전 정비 예측**: 텔레매틱스+진단 데이터 기반 수요 분산 → 서비스 부하 평탄화 → CSI 방어.
  Part 사전 준비(입고 즉시 수리)까지 체인에 포함.

## 7. UI/UX 원칙과 프로토타입

### 7.1 원칙
1. **심플하고 직관적** — 복잡한 상황일수록 화면은 단순하게. 한 화면 = 한 질문에 답한다.
2. **집계 → 드릴다운 → VIN**: 모든 숫자는 클릭하면 근거(하위 집계 → VIN 목록 → VIN 이벤트 체인)로 내려간다.
3. **월별 Play**: 과거~현재는 재생, 현재 이후는 생성된 미래. 재생 중에도 필터/뷰 전환 가능.
   (참고: 시계열 재생 + 필터 방식 — Evergreen의 animated demographics 차트 스타일)
4. **BP는 항상 기준선**: 어떤 뷰에서도 "계획 대비 지금 어디인가"가 보인다.
5. **대시보드가 아니라 트윈**: 화면 요소는 업무 객체(공장, 운송, 딜러, 고객)와 1:1로 대응하고,
   그 위에서 모델이 동작·자동화될 수 있는 구조로 만든다.

### 7.2 3가지 표현 방식 프로토타입 (가상 데이터)

| 버전 | 파일 | 관점 | 잘 답하는 질문 |
|---|---|---|---|
| **V1 밸류체인 파이프라인** | `prototypes/v1-value-chain-twin.html` | 프로세스/흐름 중심 | 지금 파이프라인 어디에 얼마나 쌓여있나? 병목은? BP 대비 유량은? |
| **V2 지오 네트워크** | `prototypes/v2-geo-network-twin.html` | 공간/네트워크 중심 | 어느 지역 재고가 위험한가? 운송은 어디를 지나고 있나? 지역별 품질/VoC는? |
| **V3 시뮬레이션 콕핏** | `prototypes/v3-simulation-cockpit.html` | 시나리오/미래 중심 | 인센티브를 올리면? 캠페인이 터지면? BP와 미래 시나리오의 차이는? |

- 세 버전은 **동일한 가상 데이터 스펙(§8)** 을 사용해 표현 방식만 비교할 수 있게 한다.
- 최종 UI/UX는 이 중 택1이 아니라 **조합**이 될 가능성이 높다 (예: V1을 홈으로, V2/V3를 탭으로).
- 각 프로토타입은 단일 HTML(외부 의존성 없음)로, 브라우저에서 바로 열어 확인한다.

### 7.3 트윈 표현 강화 버전 (V4–V6)

V1–V3 검토 결과: **직관적·심플하지만 "디지털 트윈"의 느낌이 부족** (대시보드에 가까움).
물리적 업무가 화면에서 동작하는 것처럼 보여야 하고, 판매법인을 선택하면 트윈으로 구현된
객체 리스트가 보이고, 클릭하면 그 객체의 하위 트윈으로 들어가는 **중첩(nested) 구조**가 필요하다.
핵심: **데이터가 피딩되고 → 모델이 처리하고 → 결과가 만들어지는 과정이 눈에 보여야** 한다
(예: 결과가 생산법인 3개로 전달되면, 생산법인 클릭 시 그 공장의 트윈이 열린다).

**트윈 디자인 언어 (V4–V6 공통)**
- 메인 영역은 차트 그리드가 아니라 **하나의 씬(scene)**. 업무 객체(법인·공장·운송·딜러·모델)를 도식 오브젝트로.
- **흐름 애니메이션**: 객체 간 경로 위 파티클 — 밀도·속도 ∝ 월 유량. 물류(차량)와 데이터 스트림은 시각적으로 구분.
- **폐루프**: 고객/딜러에서 나온 데이터(Retail, VoC, 텔레매틱스)가 판매법인으로 되돌아가는 피드백 스트림 필수.
- **가동감**: 처리 노드 펄스, 라이브 카운터 티킹, status 램프(아이콘+라벨).
- **중첩 드릴**: 객체 클릭 → 줌 전환으로 하위 트윈 씬 진입, 브레드크럼 내비게이션. 하위 씬에서도 집계→VIN 드릴 유지.
- 다크 기본(관제 무드), prefers-reduced-motion 시 파티클 정지.

| 버전 | 파일 | 관점 | 트윈 표현의 초점 |
|---|---|---|---|
| **V4 계층형 시스템 트윈** | `prototypes/v4-hierarchy-twin.html` | System of Systems | 판매법인 씬 → 공장/딜러 클릭 시 하위 트윈으로 줌인, 피드백 폐루프 |
| **V5 모델 파이프라인 트윈** | `prototypes/v5-model-pipeline-twin.html` | 데이터→모델→결과 | 데이터 소스 스트림이 모델 노드를 거쳐 주문서로 산출되는 처리 과정 자체를 트윈화 |
| **V6 기아 북미권역 월드 트윈** | `prototypes/v6-isometric-world-twin.html` | 물리 공간감 + 실지도 | 한국·미국·캐나다·멕시코 실지도 위 기아 공장·판매법인·딜러 5개 지역, 줌/팬, 차량 아이콘 재고 스택 |

**V6 업그레이드 결정 사항 (사용자 피드백 반영)**
- 최상위 계층은 **북미권역본부** — 판매법인 3개(Kia America / Kia Canada / Kia Mexico)가 모두 보인다.
  현 단계는 미국만 완전 구현, 캐나다·멕시코 법인은 클릭 시 주문·Wholesale 월별 집계만 표시(추후 확장).
- 실지도 레이어(한국·북미, 태평양 중심) + 마우스 휠 줌/드래그 팬.
- 대상 체계: 기아 — 오토랜드 화성(EV6·카니발, 선박 수출), Kia Georgia 웨스트포인트(텔루라이드·스포티지·EV9),
  Kia Mexico 페스케리아(K4). 딜러는 미국 5개 지역(West/Central/South/Northeast/Southeast)으로 그룹.
- 재고는 추상 블록이 아니라 **차종별 차량 실루엣 아이콘의 시각적 스택**(1아이콘=N대 스케일 캡션 + 범례).
- **최초 화면에 KPI 타일 없음** — 판매법인/생산법인은 KPI 체계가 다르므로, 엔티티 선택 시
  컨텍스트 패널에 그 주체에 맞는 KPI를 표시한다.
- **시맨틱 줌(LOD)**: 줌은 글씨 확대가 아니라 정보 상세도의 전환이다. 카드가 화면 픽셀 크기를
  유지한 채 줌인 시 지리 간격이 벌어져 겹침이 풀리고, 줌 밴드(Z1 핀+약어 → Z2 컴팩트 카드 →
  Z3 상세 카드)에 따라 표현이 교체된다. 겹침은 충돌 검사로 리더 라인/클러스터 처리.
- **계층 내비게이션**: 최초 화면은 북미권역본부 카드 1개 → 클릭 시 산하법인 전개
  (판매법인: KUS·KCA·KMX / 생산법인: KaGA 웨스트포인트·HMGMA 사바나·KMX 페스케리아) →
  KUS 선택 시 딜러 5개 지역 + 관련 생산법인 + 화성 수입 경로 → 공장/지역 내부 트윈.
  모델→공장: KaGA=텔루라이드·스포티지, HMGMA=EV9, KMX=K4,
  한국 수입 2개 플랜트 — 오토랜드 화성=EV6, 오토랜드 광명=카니발 (평택항 경유 선박 → 포트 휴니미).
  화성·광명은 지리적으로 인접 → 줌아웃 시 "한국 공장 2" 클러스터, 줌인 시 분리(LOD 대표 사례).
- **흐름 레이어 필터**: 미국 뷰에서 물류/주문서/피드백 레이어를 토글(기본 물류만 ON)하고,
  차종 칩 필터로 선택 모델의 흐름만 표시(경로 두께·파티클·배지 재계산, 무관 경로 dim).
  엔티티 호버/선택 시 연결 경로만 포커스. 물류 배지는 "대수/월 · 운송기간(일)" 형식,
  툴팁에 구간별 리드타임 분해(공장→항만/해상/항만 처리/철도 등).
- 이전 버전 보존: `prototypes/archive/v6.0-isometric-abstract.html`(추상 아이소메트릭),
  `prototypes/archive/v6.1-kia-na-map.html`(실지도 1차 — LOD 이전),
  `prototypes/archive/v6.2-lod-hierarchy.html`(LOD/계층 — 흐름 필터 이전).

### AI 에이전트 방향 (P4)
- **주문 초안 에이전트**: Retail 속도 + Days Supply + 생산 제약을 읽어 월 주문안을 생성, 담당자는 승인/수정만.
- **리스크 워처**: 시뮬레이션을 상시 재실행해 임계 초과(재고일수, 품질비, 서비스 지연)를 알림 + 근거 체인 제시.
- **시나리오 탐색기**: 파라미터 공간을 자동 탐색해 KPI 파레토 프론티어(판매–이익–만족도) 후보를 제안.
- 목표: 사람은 반복 계산에서 벗어나 **시나리오·모델 개발에 집중**.

## 10. 화면 공통 컴포넌트 규약 (프로토타입 → 실개발 공통)

- **KPI 스탯 타일 행**: 판매량 / Wholesale / 영업이익 / 고객만족도 / Days Supply — 값 + BP 대비 델타 + 스파크라인.
- **타임라인 바**: 월 슬라이더 + Play/Pause + 배속, 현재(실적/미래) 경계 표시. 미래 구간은 시각적으로 구분(밴드/점선).
- **필터 행**: 콘텐츠 상단 한 줄 — 모델, 트림, 지역, 채널, 시나리오. 필터는 화면 전체에 일괄 적용.
- **드릴다운 패널**: 집계 클릭 → 하위 차원 테이블 → VIN 목록 → VIN 이벤트 체인 타임라인.
- **알림 스트립**: 해당 월의 이벤트(생산 차질, 캠페인, 재고 경보)를 status 색+아이콘+라벨로 표시 (색상 단독 금지).
- 차트 규약: 이중축 금지, 시리즈 ≥2면 범례 필수, 직접 라벨은 선별적으로, 미래 구간은 신뢰 밴드(wash) 처리.
