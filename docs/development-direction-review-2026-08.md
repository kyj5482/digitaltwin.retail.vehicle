## 1. 유지해야 할 것 — 현 방향의 강점

### 1.1 데이터 아키텍처 (data_new/)
- **레이어 분리가 교과서적**: Raw(SAP 원형 컬럼 보존) → Staging(개명·타입·그레인 규칙 선언) → Ontology(object_id+title 규약) → Semantic(바인딩 선언) → Serving. 각 레이어에 실환경 교체 지점("SLT/CDC가 raw/를 대체", "Staging은 dbt/SQLMesh로 관리")이 명시되어 이관 사양으로서 올바른 형태.
- **SAP 도메인 모델링의 사실성**: VBAK/VBAP·VBRK/VBRP·LIKP/LIPS·EKKO/EKPO·QMEL(Z1/Q1)·VLCVEHICLE·ZSD_RDR 선정, `ZZ*` 커스텀 필드 네이밍, SHKZG 차/대변 처리 — 실제 판매법인 SAP 랜드스케이프와 부합.
- **VIN 단일 키로 밸류체인 전 구간 연결**: 매입→도매→출하→소매→VoC 체인이 실제 링크 파일 15종으로 실체화되고 `40_serve.sql` Q2로 검증됨(~10ms).
- **의사결정이 실측 기반**: Parquet vs CSV를 200만 행 벤치마크(크기 8×, 필터 28×)로 결정하고 "사람이 쓰는 파일은 CSV, 기계가 읽는 파일은 Parquet" 기준까지 문서화. 서빙 4종 질의 4~12ms 실측.
- **시점 규칙 존재**: L0 KPI는 마감월만 노출(`closeMonthlyFinance` 액션과 연결) — 미마감 데이터 통제를 의식한 설계.

### 1.2 실개발 전환 전략 (development/)
- **"md 단일 입력 소스 → 빌드 → 주입"이 실제로 관철됨**: `entity-profile.md` → `build-entity.js`(외부 의존성 0) → `entity-config.json`/`entity-config.js` → `window.ENTITY_CONFIG` 폴백 패턴. 법인명·KPI 표기·가중치·부문명은 코드 수정 없이 교체된다.
- **레벨별 데이터 계약 원칙**: L0~L3 레벨 정의와 "상위는 하위의 집계만 안다 · 인스턴스는 datasource 바인딩으로만 조회"(01-world-hierarchy.md) — 확장 시 결합도를 낮추는 정석적 트윈 설계.
- **폐루프가 1급 요구사항**: P4 단계 정의(액션 실행→원장 기록→KPI 환류), 원장 append-only·정정 이벤트 규칙 — UI 장식이 아니라 데이터 계약으로 폐루프를 뒷받침하려는 사상.
- **검증 가능한 수용 기준(AC)과 실테스트**: Playwright 회귀 89건이 실재하고 entity-config 반영·딥링크 무플래시가 테스트됨(W17).

### 1.3 의사결정 지원 설계 (비즈니스 관점)
- **What-if가 프로젝트의 중심**: 레버 5종(가격·인센티브·마케팅·재고 DS·EV 증산) → 16개월 재생성 → BP 대비 궤적·영업이익 워터폴 분해. 프리셋 5종에 트레이드오프 관전 포인트까지 정의("인센티브 $2,200 초과 시 CSI 하락").
- **"결정→실행→검증" 체인이 데이터 구조로 존재**: 시나리오 커밋→커밋 밴드 추적→프로젝트 기대 vs 실측 리뷰 원장. 대부분의 트윈이 "보기"에서 끝나는 것과 차별화되는 지점.
- **HITL/AI 위임 구분이 실무 근거 기반**: 8사 프로세스 리서치로 리콜=위임 불가 등을 정당화 — "AI가 결재권을 뺏는다"는 현업 저항을 줄이는 설계.
- **자기비판이 정직함**: `ceo-1dau-review.md`가 스스로 "주간 도구 합격, 매일 아침 도구 미달"로 판정하고 로드맵을 제시, 이후 브리핑·스코어보드·워게이밍이 실제 구현됨.

## 2. 강화해야 할 영역 — 심각도순

### 🔴 A. 데이터 배선 단절 — "데이터 이중 세계" (심각도: 최상)

**발견**: 프런트 전체에서 런타임 `fetch()`는 0건(외부 지도 CDN 1건 제외). 모든 화면(v7~v10)은 `v7-data.js`(387KB 임베드 JSON, generate.py 생성물)를 소비한다. **data_new/의 Parquet 52개·DuckDB 파이프라인을 소비하는 프런트 코드는 0건**이고, `server.js`는 125줄 순수 정적 서버로 API 라우트가 없다.

**의미**: 요구사항 AC-3("씬 문법 6종이 실데이터로 동작")의 최대 블로커. 이 배선이 없는 한 data_new/는 "돌아가는 데모"이고 프런트는 "가상 데이터 상영관"이다. 또한 387KB 전역 블롭 일괄 로드 + 브라우저 VIN 인스턴스 빌드는 자체 성능 요구("L0 첫 페인트에 L3 인스턴스 로드 금지")와 이미 충돌하며, 실볼륨(1:1 ≈ 15만 VIN)에서는 즉시 파산하는 구조다.

**권고**: 다음 스프린트의 1순위는 새 기능이 아니라 **얇은 서빙 API**다. `server.js`에 DuckDB 질의 핸들러(시멘틱 레이어의 datasource만 참조)를 얹고, v10의 **씬 1개**(예: L0 KPI 롤업 → 부문 1개 드릴)를 end-to-end로 전환하는 수직 슬라이스(vertical slice)를 먼저 완성해 배선 패턴을 확정하라.

### 🔴 B. 폐루프가 선언뿐 — 쓰기 경로 부재 (심각도: 상)

**발견**: README DAG의 "폐루프: 액션 실행→원장 append→재적재"를 실행하는 코드가 0줄. `semantic-layer.json`을 읽는 코드 자체가 저장소에 없다(참조처는 문서 2건뿐). 액션 8종의 `ledger` 필드는 실행 가능한 매핑이 아닌 서술 문자열. append 라이터, 재적재 트리거, 액션 API, HITL 게이트의 승인 권한·멱등성·감사 추적이 모두 미정의 — 4단계(P1~P4) 중 가장 위험한 P4가 가장 얇게 정의되어 있다.

**의미**: "데이터 기반 의사결정"의 후반부(결정→실행→결과 환류)가 아키텍처에 존재하지 않는다. 불변 Parquet 전량 덮어쓰기 구조에는 "쓰기 경로"라는 개념 자체가 없다.

**권고**: 실환경 착수 전에 **쓰기 계약을 사양화**하라 — ① 액션 API(파라미터·전제조건·효과 스키마), ② append 전용 원장 스토어(불변 Parquet가 아닌 append 테이블 또는 Iceberg/Delta류 테이블 형식), ③ 게이트 승인의 권한 모델·감사 로그, ④ 액션→KPI 인과 귀속(attribution) 방법. 프로토타입 수준이라도 1개 액션(예: `approveWarrantyClaim`)의 왕복을 구현해 P4의 리스크를 조기 소진할 것.

### 🔴 C. 시멘틱 레이어 이원화 + 계약 불충분 (심각도: 상)

**발견**: 의미 계층의 정본이 둘이다 — 프런트 `v7-ontology.js`(객체 31·링크 61·액션 36, stage/params/effects 보유) vs 파이프라인 `semantic-layer.json`(객체 10·액션 8, 파라미터 없음). 동기화 장치가 없고, JSON 쪽은 자기 참조 무결성도 깨져 있다(linkTypes가 참조하는 `plant`·`salesZone`·`salesCompany`가 objectTypes에 없음). 객체별 필드 스키마·타입·카디널리티가 선언되지 않아 "프런트는 이 선언을 통해서만 데이터에 접근"이라는 원칙이 필드 수준에서 성립하지 않는다. 버저닝은 날짜 문자열 하나.

**의미**: 디지털 트윈의 생명은 "의미 계층 단일 정본"이다. 이원화 상태로 실개발에 들어가면 폐루프의 의미가 화면과 데이터에서 달라지는 드리프트가 필연적으로 발생한다.

**권고**: `semantic-layer.json`을 유일 정본으로 승격하고 `v7-ontology.js`를 **빌드 생성물**로 전환(build-entity.js와 같은 패턴). 이때 v7-ontology.js가 이미 가진 카디널리티·액션 파라미터·효과 스키마를 JSON 계약에 역이식하고, semver + 호환성 규칙, 그리고 **이 JSON을 실제로 로드해 질의를 생성·검증하는 코드**를 함께 만들 것.

### 🔴 D. 유연성이 "표기 치환" 수준 — 구조의 데이터화 필요 (심각도: 상)

**발견**: entity-config가 오버라이드하는 것은 법인명·KPI 이름/가중치·부문 이름/오너뿐이다. 구조는 전부 코드 내장 — `ROOT_ID='SC-US'` 고정, 형제법인 최대 2개(키 `'SC-CA'`,`'SC-MX'` 고정), 9부문 DEPTS의 스텝·액션 매핑·KPI 연결 전부 HTML 리터럴, KPI 트리 위상은 v7-data.js 내장, 소환 월드 5종 경로 하드코딩. 신규 KPI는 ceo_tree.csv에 없으면 산출물에서 탈락한다. 파서가 추출하는 필드의 상당수(BP 목표·데이터소스·통화·회계연도)는 프런트에서 소비되지 않아 README의 반영 범위 서술이 과장이다. 다법인(프로필 N개→월드 N개, 법인 간 비교·통화 환산·연결 집계) 요구는 어디에도 없다.

**실버그 1건**: `build-entity.js:25`의 `blank()`가 `'-'`를 미입력으로 취급하는데, KPI 방향 컬럼의 "낮을수록 좋음"이 정확히 `-`다 → KPI-GREEN·KPI-SEC의 `dir`이 조용히 소실되어 달성률 계산이 반대로 나올 수 있다. **즉시 수정 필요.**

**권고**: ① blank 센티널과 방향 컬럼 분리(즉시), ② 월드 레지스트리(01 문서에 "예시"로만 존재)를 entity-config 빌드의 정식 산출물로 승격해 조직 형태·부문 구성·씬 구성을 데이터화, ③ 미소비 프로필 필드(target·source·currency)의 프런트 연결, ④ 법인 2호기 온보딩 절차를 요구사항에 추가. 이것이 없으면 2호기부터 v7→v8 포크(5.4천 라인 중복)의 재현이다.

### 🟡 E. 실SAP 전환 시 깨지는 지점 (심각도: 중~상, 이관 착수 전 필수)

- **채번 파생 조인**: `20_stage.sql`이 빌링·납품을 `'90'||substr(VBELN,3)` 문자열 수술로 조인 — 실SAP에서 문서 번호는 파생 불가능하며 **VBFA(문서흐름)** 로 연결해야 한다. "이후 단계는 그대로 재사용된다"는 README 주장이 이관 시 오판을 유발할 수 있다.
- **품질 게이트 0개**: 전 파이프라인에 검증 문장이 없다 — PK 유일성, 행수·금액 대사(FI 400100 = VBRK 합계), 고아 링크 검사, load_ts/batch_id 감사 컬럼 전무. 실패 시 부분 산출물로 남는다.
- **증분 적재 부재**: 전 단계 전량 덮어쓰기. hive 파티션은 언급뿐 미구현. CDC merge·late-arriving·마스터 SCD 개념 없음.
- **회계 기간 불일치**: 매출은 도매월, COGS는 **생산월** 기준 전기 → 월별 매출총이익이 리드타임만큼 진동하는 왜곡. 시점 게이트(마감월)도 L0에만 적용되고 L2/L3 질의는 미래 일자 실적을 그대로 집계.
- **동시성 미검증**: DuckDB `:memory:` 단일 프로세스 데모뿐 — 커넥션 전략, Parquet 교체 중 읽기 일관성(스왑 원자성)이 미설계.

**권고**: 실데이터 연동 P2 착수 전 체크리스트로 반영 — VBFA 조인 재작성, dbt/SQLMesh류 테스트 계층, 파티션 단위 증분(또는 테이블 형식 도입), COGS 판매월 인식, 시점 게이트의 서빙 공통 규칙화. 특히 **숫자 신뢰**는 이런 프로젝트의 전형적 실패 경로다: 실데이터 전환 시 기존 보고 숫자와 불일치가 나면 현업 신뢰가 급락한다 — 레이어 간 대사(reconciliation) 자동 검증을 "있으면 좋은 것"이 아니라 필수 게이트로.

### 🟡 G. 비즈니스 가치의 정량화·검증 (심각도: 중, 경영 승인 관점)

- **ROI 가설 부재**: 전 문서를 통틀어 정량 가치는 HVAC "월 ≈ $10만 절감" 1건뿐. "인센티브 효율 x% / 재고비용 y 절감" 같은 가치 가설·검증 지표·기간이 없어 경영 투자 승인용 비즈니스 케이스가 별도로 필요하다.
- **예측·AI가 v0 수준임을 명시적으로 관리**: "학습 기반 예측"의 실체는 시즌 지수+선형 추세, "AI 워게이밍"은 레버 조합 열거+결정론 수식 랭킹이다. 탄력성 파라미터는 문헌 가정치 — 자사 실적 캘리브레이션·백테스트가 P2 이후 필수 과제. "시뮬레이션을 믿고 결정해도 되는가"에 대한 답(백테스트 정확도 공개)이 채택의 관문이다.
- **일 단위 심박 미구현**: 전 데이터가 월 파티션 — "어제와 오늘 화면이 같다"는 재방문 저해 요인이 미해결. CEO 1-DAU 6요소 중 브리핑·스코어보드·워게이밍은 구현, **일 펄스·회의 워크플로·레버 매트릭스는 미구현** — 현 상태는 문서 스스로의 판정대로 "주 1~3회 도구".
- **경쟁·시장 축 부재**: SAAR·세그먼트 점유율·경쟁사 인센티브가 없어 "점유율 방어" 유형 의사결정 불가(자체 리뷰도 자인).
- **채택 리스크**: 트윈의 결재함이 기존 시스템(SAP 결재·딜러 포털)을 대체인지 병행인지 미정의 — "또 하나의 봐야 할 화면"이 될 위험이 최대 채택 리스크. 부문 담당자 고유 효용(조기 경보·공수 절감)의 정의·측정 계획도 없어 CEO 의존 top-down 구조.

## 4. 결론

설계 사상 — 레이어드 파이프라인, 시멘틱 계약, md 단일 입력, 폐루프 1급 요구, 실측 기반 의사결정 — 은 디지털 트윈 실개발의 정석이며 **변경할 이유가 없다.** 그러나 현재 상태는 "표현(프런트)과 데이터(파이프라인)가 각자 완성도 높게 존재하되 서로 연결되지 않은" 구조이고, 유연성은 표기 치환 수준이며, 폐루프는 선언 단계다. 따라서 **"현재를 유지해서 지속 개발"이 아니라 "방향 유지 + 강화 4대 과제(배선·쓰기 경로·시멘틱 정본·구조 데이터화)를 P1~P2에 전진 배치"** 가 권고안이다. 특히 다음 개발 단위는 기능 추가가 아니라 수직 슬라이스 1개(실데이터 씬 1개 + 액션 1종 왕복)로 잡아, 가장 큰 미지수(배선 패턴·쓰기 계약)를 가장 먼저 소진할 것을 권한다.
