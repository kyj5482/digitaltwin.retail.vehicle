# 00. 실개발 전환 개요

## 목적

v10 프로토타입(디지털 트윈 월드)이 검증한 문법 — 관계뷰 씬 · 계층 드릴다운 · Play 타임라인 ·
폐루프 환류 — 을 유지한 채, **특정 판매법인 1개**를 대상으로 실데이터 기반 개발로 전환한다.

## 범위 — 3층 구조 (프로토타입과 동일)

| 층 | 프로토타입 (현재) | 실개발 (목표) |
|---|---|---|
| 데이터 | `data/*.csv` 가상 생성 (`_generator/generate.py`) → `v7-data.js` | 법인 DW/parquet 마트 — 그레인·주기 계약은 `data/SCHEMA.md` 승계 |
| 온톨로지 | `v7-ontology.js` 타입 선언 + `v7-ontology-instances.js` 표본 | 동일 타입 체계 + 실데이터 바인딩(`datasource.path`) — **월드 레벨별 서브그래프**로 분할 |
| 월드(Frontend) | `v10-twin-world.html` 단일 문서 + iframe 소환 월드 | 계층형 월드 레지스트리 — 레벨별 라우팅 · 상태 선적용(무플래시) |

## 입력물과 반영 경로

- **`development/entity-profile.md`** — 법인명·조직·KPI·부문·데이터 인벤토리의 단일 입력 소스.
- `node development/tools/build-entity.js` → `prototypes/entity-config.js` 생성 → 프런트 반영.
- 요구사항 문서(01~03)는 이 프로필을 채운 뒤 해당 법인 기준으로 구체화한다.

## 진행 단계

| 단계 | 내용 | 산출물 | 완료 기준 |
|---|---|---|---|
| P1 프로필 확정 | entity-profile.md를 실제 법인 값으로 입력 | entity-config.js | 트윈 월드에 법인명·KPI 반영 확인 |
| P2 데이터 매핑 | 데이터 인벤토리 → 온톨로지 바인딩 설계 | 02 문서의 매핑 표 완성 · 마트 DDL | 레벨별 데이터 계약 검증 통과 |
| P3 월드 구현 | 계층형 월드 레지스트리 · 라우팅 · 씬 이식 | 법인 트윈 월드 v1 | 01 문서의 수용 기준(AC) 전건 통과 |
| P4 폐루프 | 액션 실행 → 원장 기록 → KPI 환류 연결 | 게이트·에이전트 연동 | 실행 피드에서 실데이터 왕복 확인 |

## 전환 원칙

1. **문법은 유지, 값만 교체** — 씬·드릴·Play·폐루프의 상호작용 문법은 프로토타입이 사양(spec)이다.
2. **계층 = 온톨로지** — 모든 화면은 온톨로지 노드의 시점(view)이며, 레벨마다 자기 데이터 계약을 가진다.
3. **md 입력 → 빌드 반영** — 법인 고유 값은 코드에 하드코딩하지 않는다. 프로필 문서가 유일한 출처.
4. **무플래시 전환** — 어떤 딥링크·재소환 경로에서도 이전/기본 제목줄이 보이지 않는다 (01 문서 AC).
